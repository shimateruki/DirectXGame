# 衝突判定と A* 経路探索を計算から読む

[目次](00_目次と読み方.md) / [実行時システムの概要](08_実行時システム.md)

## 1. 「当たる」と「避けて進む」は別の問題

衝突判定は、現在の形状同士が重なるか、移動先で何に触れるかを答える。経路探索は、通行可能とされた場所をつないで目標までの道筋を答える。経路が得られても、その通りの速度で移動する処理、床への接地、押し戻しは別に必要になる。

このプロジェクトでは [`CollisionManager`](../engine/system/collision/CollisionManager.cpp) が衝突相手と Query を管理し、[`NavGrid`](../engine/system/navigation/NavGrid.cpp) が通行情報と経路を作り、[`NavAgentComponent`](../engine/component/NavAgentComponent.cpp) が次に向かう方向を返す。`CalculateDirection` の返り値は位置でも速度でもなく、原則として XZ 平面上の正規化方向である。

## 2. 広域判定：空間グリッドへ形状を登録する

全対象を総当たりすると、N 個の相手の組合せは N(N−1)/2 個になる。1,000 個なら 499,500 組である。広域判定（Broad Phase）は、正確な形状計算をする前に「遠いから当たらない組」を減らす段階である。

`CollisionManager::Update` は動的対象の AABB（軸に平行な境界箱）が占めるセルを調べ、そのすべてへ対象を挿入する。中心のセルだけに登録すると、セル境界をまたぐ大きな形状が隣の対象を見落とすためである。静的対象のグリッドは dirty のときに再構築し、動的対象のグリッドは更新ごとに作り直す。

同じ二つの動的対象が複数セルに存在する場合、同じ組を何度も発見できる。動的同士はペアを正規化して `checkedPairs_` で重複を除く。一方、動的対静的は現行コードでセルごとに再判定する。既存の押し戻しとの関係から、動的対象を先頭にした評価順も保持している。したがって「各ペアは必ず一度だけ処理される」とは説明できない。

グリッドは密集した全対象を魔法のように減らせない。同じセルに大部分が集まれば候補数が増え、大きな対象は登録セル数も増える。セルサイズは候補密度と登録コストの交換条件になる。

## 3. 詳細判定と衝突通知

`CheckCollisionPair` は属性とマスクを両方向に確認する。概念的には次の条件である。

```text
(A の mask & B の attribute) != 0
かつ
(B の mask & A の attribute) != 0
```

属性は「自分の分類」、マスクは「相手として受け入れる分類」のビット集合である。一方の設定だけで許可しても通らない。これを通過してから Collider の形状別の詳細判定（Narrow Phase）へ進む。

接触が得られると従来の `OnCollision` が両側に呼ばれ、現在の接触集合にも記録される。後段の `DispatchContactEvents` は現在と前回の集合を比較する。

| 前回 | 今回 | 意味 |
| --- | --- | --- |
| なし | あり | Enter：接触開始 |
| あり | あり | Stay：接触継続 |
| あり | なし | Exit：接触終了 |

相手側へ渡す法線は向きが逆になる。A から見た押し戻し方向を B にそのまま渡せば、双方が同じ方向に押されてしまう。ペアの記録順と通知先をそろえる必要がある。

ここで従来の `OnCollision` と Enter/Stay/Exit は同じ呼出頻度ではない。前述の静的対象との再判定により、前者は一更新内で複数回呼ばれうる。ダメージの一回制限を考える際は、どの通知を使っているかと、ゲーム側が持つクールダウンや接触履歴を確認する。

## 4. Query は通常の接触処理と別の経路

`OverlapSphere` と `OverlapAABB` は、登録された対象を走査してフィルターを適用し、一時的な Collider との重なりを調べる。通常更新がグリッドを使うからといって、すべての Query も同じグリッドで高速化されるわけではない。

`OverlapCapsule` は線分上に球を並べて調べる近似である。線分長と半径に応じたサンプル数を使い、同じ Object が複数の球に重なった場合は重複を除いて深い接触を残す。解析的なカプセル対形状計算と同じものではない。

`SphereCast` / `CapsuleCast` も一定距離ずつ進めて Overlap を調べる方式で、移動刻みの基準は `max(0.05, radius * 0.5)`。最初にヒットしたサンプル位置で結果を選ぶ。

例えば半径 0.2 なら基準刻みは 0.1、距離 2 の区間にはおおむね 20 分割が必要になる。結果の距離はその離散位置に依存する。連続した時刻の最初の接触（TOI: Time of Impact）を厳密に解いているわけではない。細い形状、小さな半径、斜めの接触では刻みと形状の関係に注意する。移動距離が長いと Query 回数も増える。

## 5. 経路用グリッド：障害物を半径分広げる

`NavGrid::Build` は XZ の平面グリッドを作る。高さは `planeY` に固定される。セル数は概ね `ceil(範囲 / cellSize) + 1`、ただし軸ごとの上限で切られる。`NavAgentComponent` はその上限を 64 にしている。セルサイズを保ったままセル数を制限するので、遠い目的地まで常に元の範囲を完全に表現できるという意味ではない。

障害物収集は範囲全体の `OverlapAABB` を一度呼ぶ。その結果の AABB を各セルへ塗り込む。セルごとの Query を繰り返す設計ではない。

障害物の XZ をエージェント半径 r だけ広げる処理は、配置空間（Configuration Space）の考え方に相当する。「半径のあるキャラクター」を動かす問題を「膨らませた障害物の間で点を動かす問題」へ近似変換する。

```text
障害物の X 範囲 [2, 3]、エージェント半径 0.4
→ 中心が避ける範囲 [1.6, 3.4]
```

ただし実装は障害物 AABB の各軸を広げ、セルへ保守的に塗る。丸い物体の外形や斜めの壁をぴったり表現するものではない。狭い通路が実際より閉じやすくなる代わりに、中心だけを通して身体が壁へめり込む経路を抑える。

低い床面は `planeY + max(0.15, radius * 0.30)` 以下なら障害物から外し、頭より上の形状も除く。これは平面上の高さ条件であり、坂の歩行面を構築したり、上下に重なる複数の階を表現したりする NavMesh ではない。

## 6. ワールド座標とセル座標

`WorldToCell` は `(position - boundsMin) / cellSize` を丸めて整数にする。その後、範囲外も最寄りの端へ clamp する。戻り値 true は「元の位置が範囲内だった」ことを保証せず、グリッドが構築済みであることを前提に変換できたことを意味する。

始点や終点が塞がっていれば `FindNearestWalkable` が四角い輪を広げ、最初に見つかった通行可能セルへ補正する。この「最寄り」は探索順に依存し、連続空間でユークリッド距離が最小の点を最適化しているわけではない。

## 7. A* の f = g + h は何を選ぶのか

`FindPath` は A* を使う。各セルに、それまでの最良コスト `cost`、たどってきたセル `parent`、処理済み `closed` を用意し、`priority_queue` から推定総コストが最小の候補を取り出す。

- g：始点からここまで実際にたどったコスト。
- h：ここから終点までの推定コスト。
- f = g + h：候補を調べる優先度。

上下左右の一歩を 1、斜めを √2 とする。斜め移動可能な場合の推定は octile distance である。

```text
d = min(abs(dx), abs(dz))
h = abs(dx) + abs(dz) - 2d + √2 d
```

例えば差が X=4、Z=2 なら、斜め二歩と横二歩で `h = 2√2 + 2 ≒ 4.828`。障害物があれば実経路はこれより長くなる。斜めを無効化した場合もこの推定式を使うので、四方向だけの必要距離より控えめな推定になる。

隣のセルへ行く新しい g が、そこへ既に到達した g より小さい場合だけ親とコストを更新する。終点に達したら parent を逆にたどり、最後に配列を反転する。探索途中の候補配列そのものが完成経路ではない。

## 8. 斜めの角抜けと経路の簡略化

斜めの目的セルが空いていても、その斜め移動に接する二つの直交セルのどちらかが塞がっていれば進めない。これが corner cutting の防止である。

`SimplifyPath` は前後の方向が同じ中間点を取り除く。一直線上の十個のセルを毎回目標にする必要はないためである。ただし遠い点同士の見通しを Ray で調べて角を省く処理ではなく、曲線フィットでもない。曲がり角は残る。

元の目的セルが通行可能なら入力された正確な XZ を最後に追加するが、Y は `planeY` に置き換わる。前述の範囲外 clamp と合わせて読む必要があり、「追加した最終線分も全区間検証済み」とは扱えない。

## 9. NavAgent はいつ再探索するか

`CalculateDirection` は、経路が空、目標がセル幅の半分より大きく移動、再探索タイマー満了のいずれかで `RebuildPath` を呼ぶ。自身と子を障害物から外し、Trigger も除く。

次の経由点への距離が `max(stoppingDistance, cellSize * 0.35)` 以下になると、その点を通過済みにする。最後まで到達した場合や探索失敗の場合は、目標への直接方向へ戻る。これは追跡処理を止めないためのフォールバックで、壁を避けられる保証はない。

呼出側は方向に移動速度と dt を掛け、実際に移動し、必要な衝突解決を行う。「探索に成功したか」「方向を得たか」「実際に移動できたか」は別々に観察する。

## 10. 調整時に見る対応関係

| 症状 | 最初に追う値と処理 |
| --- | --- |
| 狭い道を選ばない | agentRadius、cellSize、AABB 膨張とセル塗り |
| 遠い場所で直進する | 検索範囲、64 セル上限、探索失敗時の直接方向 |
| 曲がり角で引っ掛かる | 経由点到達距離、移動速度、実際の Collider サイズ |
| 高低差に対応しない | planeY 固定というデータ表現 |
| 接触中に処理が何度も走る | 従来 OnCollision と Enter/Stay 通知の使い分け |
| Cast が重い | 移動距離 / 刻み、各 Overlap の対象走査 |

ここで示したのはコードから分かる構造であり、各ステージの通行性を実行検証した結果ではない。
