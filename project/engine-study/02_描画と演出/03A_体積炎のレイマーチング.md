# 体積炎はどのレイマーチングをしているか

[目次](../00_目次と読み方.md) / [シェーダー概要](03_シェーダーとマテリアル.md)。対象は [`FireVolume.hlsli`](../../Resources/shader/materials/FireVolume.hlsli) の `RenderFireVolume`。名前だけで「レイマーチング」と覚えると、SDF 表面探索や画面空間反射と混同するため、画素一つを計算する順番で読む。

## 1. 描くのは物体の表面ではなく、中を通る光

通常の Mesh は三角形の表面を描く。体積炎では閉じた代理形状（proxy）の画素を入口にし、その内側を視線がどれだけ通り、どの位置に濃い炎があるかを計算する。外形の三角形を増やすだけでは炎の内部の透け方は表現できない。内側の密度と発光色を複数箇所で評価して合成することで、横からも上からも厚みが変化する。

現行方式は**固定サンプル数の volume ray marching**。視線上の区間を 24 または 32 分割し、各中点で密度と色を取る。SDF が返す「最寄り表面までの距離」だけ進む sphere tracing ではない。`FireDensityHeat` が返すのは密度と見た目用の heat であり、幾何学的に保証された距離ではない。したがって、その値をそのままレイの安全な歩幅にはできない。

## 2. 一画素からワールド空間の視線を作る

Pixel Shader に渡る `input.pos.xy` は描画先の画素位置。深度 Texture の幅・高さで割り、0～1 の UV にする。同じ UV について深度 0 と 1 の位置を `FireWorldPosition` で復元する。

```text
clip = (2u-1, 1-2v, depth, 1)
worldH = clip × inverseViewProjection
world = worldH.xyz / worldH.w
ray = normalize(farPoint - nearPoint)
```

Y が `1-2v` なのは、画像の上から下へ進む UV と Clip 座標の上下を合わせるため。最後の w 除算は同次座標から通常の 3D 座標へ戻す操作。単に xyz だけ取り出すと透視投影の距離が壊れる。`waterInverseViewProjection` という名前を共有しているが、ここでは炎の深度復元にも使っている。

Near / Far の定数を別途ハードコードせず、現 Camera の逆行列から復元する。そのため投影が変わった際も、正しい行列が供給されれば同じ経路で視線を作れる。深度が別カメラ・別解像度のものなら UV と位置の対応が崩れる。

## 3. Worldから正規化した炎の空間へ

炎の中心を World 行列から取り、視線の始点と方向を World の逆変換でローカル側へ戻す。さらに `extent` で割って、炎の評価領域を各軸おおむね -1～1 に揃える。この正規化により、炎の密度関数は Object の実サイズが変わっても同じ範囲で計算できる。

始点には中心を引くが、方向には平行移動を適用しない。方向は長さと向きだけであり位置ではないため。ローカル変換後の `direction` は再正規化されていない。これはもとの World の ray 上の距離パラメータを維持して箱との交点を扱うためで、後で `length(direction)` がローカル空間のサンプル間隔へ換算する。

`effectScale`、軸別 Scale、`billboardScale` はここで extent に作用する。色を変えるパラメータとは作用位置が違う。炎が横に伸びる問題を色の強度で直しても根本は変わらない。

## 4. 箱への入射・退出はslab法

視線 `p(t)=origin+direction*t` と箱の各軸の範囲 [-1,1] を考える。X 軸なら `(-1-origin.x)/direction.x` と `(1-origin.x)/direction.x` が二つの面を通る t。方向が負の場合に順序が逆になるので min / max で揃える。Y、Z も同様。

三軸すべての範囲へ入る時刻は「各軸の入口の最大値」、どれか一軸から外れる時刻は「出口の最小値」。これが `start` と `finish`。`finish<=start` なら有効な体積を通らないので discard する。

direction がほぼ 0 の軸は ±1e-6 へ寄せ、ゼロ除算を避ける。これは平行なレイを扱うための数値上の対策。閾値の意味を知らず消すと、特定角度で NaN や極端な値が出やすくなる。

Proxy の退出面を使うため `dot(input.normal,ray)<=0` の面を除外する。入口面だけを頼ると Camera や Near 面が体積の内部に入ったとき、その入口面が視野に存在しないことがある。退出面から画素を得ることで、その状況でも内部の区間を計算できる。

## 5. 不透明な壁を突き抜けないよう終点を短くする

背景深度から壁表面の World 位置を復元し、`dot(background-nearPoint,ray)` で視線に沿う距離を求める。`finish` をその距離以下に制限する。炎と壁が交差したとき、体積全体を消すのではなく、壁より手前の部分だけ積分する。

深度 Texture は通常、手前の不透明面しか持たない。複数の透明体の内外関係をこの値だけですべて解くことはできない。ここで成功しているのは不透明な背景との深度整合であり、あらゆる透明物体の順序独立合成ではない。

## 6. 密度を作るノイズは流体計算ではない

`FireNoise3` は整数格子の八隅に hash 値を作り、セル内の位置を `f*f*(3-2*f)` で滑らかにして三線形補間する **3D value noise**。単に乱数を毎画素で独立に取ると粒々のちらつきになるが、隣り合う点の値が滑らかにつながれば塊として見える。

`FireDensityHeat` は座標を時間で移流させ、低周波と高周波のノイズを混ぜる。高さに応じて中心を曲げ、輪郭や根元・先端を smoothstep で削る。これにより「上へ流れる」「先端が細い」「縁がちぎれる」を作る。流体の圧力を解いて質量保存を満たすシミュレーションではなく、密度場を手続き的に生成する見た目のモデル。

`effectType` により通常炎、炎ブレス、炎柱、扇状の特殊炎へ評価関数を切り替える。色もそれぞれの heat に応じて選ぶ。heat は熱力学の温度単位 K ではなく、明るい中心と暗い外側を作るための正規化された表現値。色の数値が 1 を超えるのは HDR の発光を意図したもの。

## 7. 一サンプルの不透明度

区間の長さを steps で割り、各小区間の中央で密度を取る。中点を使うため `i+0.5` がある。サンプル間のローカル距離を `localStep` とすると、各小区間の不透明度は次の式。

```text
opacity = 1 - exp(-density × localStep × opacityScale)
```

これは Beer–Lambert 型の指数減衰を使った近似。密度が倍でも opacity は単純に倍にはならず、濃くなるほど 1 に近づく。距離を式へ含めることで、steps を増やして一回の区間が短くなったとき、各サンプルの opacity も薄くなる。単に `alpha=density` とすると、サンプル数を倍にしただけで全体が極端に濃くなりやすい。[NVIDIA の体積描画解説](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-39-volume-rendering-techniques)では、吸収・発光の離散合成を学べる。

ここで使う opacityScale は現行見た目用の係数。物理単位の消散係数を計測しているわけではない。積分にローカル空間の長さを使うため、物体拡大時の密度変化も実世界の煙の濃度保存と同一にはならない。

## 8. 前から後ろへ合成する

`transmittance` は「この位置までの手前の炎を通り抜けて残った割合」。初期値は 1。各サンプルを以下で足す。

```text
weight = transmittance × opacity
accumulated += weight × sampleColor
transmittance *= 1 - opacity
```

例えば手前の opacity が 0.2 なら、その色を 0.2 倍足し、透過率は 0.8。次の opacity が 0.5 なら色の重みは 0.8×0.5=0.4、透過率は 0.4。二つを通った最終 alpha は `1-0.4=0.6`。単純に 0.2+0.5=0.7 とする計算ではない。後ろの発光は手前を通る分だけ弱くなる。

透過率が 0.025 未満なら残りはほぼ見えないため break する。**early ray termination** と呼べる省略であり、最大サンプル数に達する前に計算を打ち切れる。描画費用は主に画面に占める面積×サンプル回数×密度関数の費用。Proxy のポリゴン数だけ減らしても Pixel Shader の重さは残る。

## 9. 最後にalphaで割る理由

`accumulated` は既に opacity を掛けた色。現行の通常ブレンドは RGB へ alpha を掛ける前提なので、そのまま渡すと alpha が二回掛かる。そこで `accumulated/alpha` を RGB として返し、alpha を別に返す。これは **premultiplied color から straight alpha color への変換**。alpha が 0 に近いときの除算を守るため `max(alpha,0.0001)` を使う。

この Shader だけを別の Blend State へ移植するときは、出力が straight か premultiplied かを確認する。見た目が暗いから発光強度を増やす前に、ブレンドの約束が合っているかを調べる。

## 10. 技術と見た目の対応

| 見え方 | 関係する技術・式 | 主に読む関数 |
| --- | --- | --- |
| 中心が濃く外側が透ける | 経路長、指数減衰、前から後ろへの積分 | `RenderFireVolume` |
| 上へ炎が流れる | ノイズ座標の時間移動 | `FireDensityHeat` 等 |
| 炎先端が揺れる | 高さ依存の座標変形、複数周波数のノイズ | 各密度関数 |
| 壁との交差が自然 | 背景深度から復元した位置による終点制限 | `FireWorldPosition`、積分区間計算 |
| 体積内へCameraが入っても描く | 退出面と start の0制限 | 面の discard、slab 交差 |
| 高輝度部分が光って見える | HDR 色と後段の画面処理 | 色関数、PostEffect |

レイマーチングを採用したという一文は、このうち「視線に沿って複数点を評価する」部分しか説明していない。座標復元、密度設計、積分、合成がつながって初めて現在の炎の見え方になる。
