# タイムラインの描画、時間、イベント、カーブ

[目次](00_目次と読み方.md) / [VFX 制作の概要](05_VFXエディターとシーケンサー.md)。対象は [`VFXSequencerEditor`](../engine/utility/SystemDebug/editor/vfx/VFXSequencerEditor.cpp)、[`VFXSequencer`](../engine/graphics/particle/VFXSequencer.cpp)、[`VFXAuthoring`](../engine/graphics/particle/VFXAuthoring.h)。時間軸は専用の魔法の部品ではなく、座標変換、マウス操作、データ構造、再生ロジックを組み合わせて作っている。

## 1. 秒を画面の横位置へ変換する

VFX の Timeline は ImGui の `InvisibleButton` でマウスを受け取る長方形領域を作り、`ImDrawList` の `AddRectFilled`、`AddLine`、`AddText` でバー、目盛り、文字を描く。通常のボタン部品だけで構成した画面ではなく、**ImGui 上のカスタムキャンバス**である。

左端が x0、幅が W、表示秒数が T なら、時刻 t の横位置は `x=x0+(t/T)*W`。W=600 px、T=3 秒なら 1 秒のイベントは左端から 200 px。縦位置は `headerHeight + eventIndex*rowHeight` なので、イベントごとに一行を持つ。画面上の行番号は再生順を自動的に決めるものではない。

瞬間的なイベントは幅がほぼ 0 になるので、バー幅に最小 8 px を設ける。これはクリックしやすくする **hit target の拡張**。8 px のバーが表示されるから、その長さぶん実際に効果が継続するわけではない。

## 2. バーをドラッグすると時刻が変わる理由

クリックの Y 座標から `floor((mouseY-y0-headerHeight)/rowHeight)` で対象行を求め、X がバーの範囲内ならドラッグ開始とする。開始時に `dragStartTime_` と表示秒数 `dragTimelineDuration_` を保存する。

ドラッグ中は `newTime=startTime+mouseDragDeltaX/W*T`。マウスが右へ 100 px、W=600、T=3 なら +0.5 秒。`GetMouseDragDelta()` は押した位置からの**総移動量**なので、毎フレーム現在時刻へ足すと移動を重複加算する。開始時刻へ加えることで正しい差分になる。表示秒数も開始時の値へ固定し、途中の UI 変化で換算倍率が跳ねないようにする。

スナップ有効なら `round(newTime/0.05)*0.05`、最後に 0～120 秒へ clamp する。スナップは編集値を丸める処理であり、再生更新が 0.05 秒刻みに変わるわけではない。再生中の変更は無効にし、実行中の `hasFired` とイベント時刻が矛盾しにくくしている。

## 3. イベントはAsset値と再生中の値を持つ

[`VFXEvent`](../engine/graphics/particle/VFXSequencer.h) は種類、参照プリセット、triggerTime、offset、duration、強度等に加え、`hasFired`、`isFinished`、画面効果へ既に足した値を持つ。前者は作った演出の設定、後者は今回の再生の進み具合。JSON を保存するとき、この二種類を同じ意味で扱ってはいけない。

`Play` は `Reset` してから再生フラグを立てる。`Update` は deltaTime がほぼ 0 なら戻り、現在時刻へ加算し、全イベントを走査する。まだ `currentTime<triggerTime` なら待機し、時刻を越えたイベントを種類別に処理する。

「0.5 秒ちょうどに呼ばれたら発火」という浮動小数点の等値比較ではないので、0.49→0.51 と跨いでも発火する。一方、複数イベントを一度に跨いだ場合、このループは `events_` の格納順に処理する。時刻順ソートをして厳密なサブフレーム順序で実行する仕組みと同一ではない。

## 4. 一回の要求と継続処理

| 種類 | Sequencerの主な仕事 | その後の寿命を持つ側 |
| --- | --- | --- |
| GPU Particle | 時刻到達時に Emit を要求 | GPUParticleSystem の各粒子 |
| Mesh Effect | プリセットから効果を生成 | MeshEffectManager / EffectObject3d |
| Sound | 再生を要求 | AudioPlayer側 |
| Moving Particle | duration 中、移動する位置から更新ごとに Emit | 軌道はSequencer、出た粒子はGPU側 |
| PostEffect Pulse | 毎更新、前回の自分の寄与を除き現在の寄与を追加 | Sequencer |
| Light Pulse | 最初に一時ライトを要求し、終了時刻までイベントを管理 | LightManager側のPulse |
| Shake / FOV / Rumble等 | 対応するシステムへパラメータを渡す | 各実行時システム |

`isFinished=true` になっても、既に発生した粒子までその瞬間に消えるわけではない。`Stop` は Reset へ進み、Sequencer が持つ発火状態と Post Pulse の寄与を戻すが、独立した Manager へ渡したすべての効果を一律に破棄する API ではない。Editor の restart が Mesh を Clear、GPU を Reset しているのは、Sequencer の Reset だけでは残る効果があるから。

`GetDuration` も全粒子の消滅時刻を調べるものではない。継続型は `triggerTime+max(duration,0.01)`、GPU 粒子等の単発型は `triggerTime+0.08` として最大値を取る。GPU プリセットの emitLife=2 秒だから Timeline の長さも必ず 2 秒増える、という関係ではない。

## 5. Moving Particleは二次Bezier曲線

開始 P0、制御点 P1、終了 P2 を持ち、`CalculateBezier` はまず P0→P1 と P1→P2 を同じ t で線形補間し、得た二点を再び t で補間する。展開すると以下。

```text
B(t) = (1-t)² P0 + 2(1-t)t P1 + t² P2
```

P0=(0,0,0)、P1=(0,4,0)、P2=(4,0,0) なら t=0.5 で B=(1,2,0)。曲線は一般に P1 を通らず、P1 に引かれるように曲がる。制御点を中継地点と誤解すると調整が合わなくなる。

進行率は `(currentTime-triggerTime)/duration`。Easing はこの t を変換するので、経路の形と、経路上を進む速度を分離できる。ただし二次Bezierの t を等間隔にしても距離は等間隔ではない。現行は弧長による等速化をしているわけではない。さらに毎更新 Emit するため、発生密度は更新回数の影響も受ける。見た目の粒間隔を揃えたい場合には距離基準の Emit 等が代案になる。

## 6. なぜ画面効果の「前回分」を覚えるか

PostEffect の共有パラメータへ毎フレーム強度を足し続けると、再生中に値が累積して戻らない。`RemovePostPulseContribution` が前回自分の足した値を引き、`ApplyPostPulse` が現在の envelope に応じた値を足す。その量を `applied*` に保持する。

これは共有パラメータへ複数の演出が寄与するための加算方式。全体の基準値を勝手に 0 へ戻すと他の演出まで消してしまう。Reset 時にも自分の寄与を除く必要がある。コードコメントに「停止する」とだけ書いても、この後始末の理由は伝わらない。

Hit Stop の残り時間は倍率の掛かっていない時間で更新する入口を持つ。ゲーム時間を 0 にしたまま、その同じ 0 の時間で停止タイマーを減らそうとすると永遠に終了できないため、時計を分ける必要がある。

## 7. キーフレームのカーブは時間を二段階で変換する

[`VFXFloatCurve::Evaluate`](../engine/graphics/particle/VFXAuthoring.h) は昇順の keys から対象区間を探し、その区間のローカル時間 `u=(t-left.time)/(right.time-left.time)` を求める。次に**左キーの Easing**で u を変換し、値を lerp する。キーが空なら fallback、一個ならその値、範囲外なら端の値。`Normalize` は時刻を0～1へ収めて stable_sort するが、Evaluate 自身が毎回ソートするわけではない。

例えば左キー (0.2,2)、右キー (0.6,10)、評価 t=0.4 なら u=0.5。Linear なら値6、EaseInの `u²` なら u'=0.25 で値4。キー位置は同じでも途中の変化が違う。色の場合は RGBA を成分ごとに補間し、この関数内で sRGB→linear 変換はしない。

共通 `VFXCurveEasing` の番号は 0～4。一方 GPU の `ParticleCS.hlsl::ApplyEasing` は 0～30 の別表。整数値が同じだから同じ曲線とは限らない。番号を変換する箇所と、Editor から実行設定へ書き戻す箇所を確認する。

## 8. Bakeとは編集用データを実行しやすい形へ変えること

`VFXBakedFloatCurve` 等は8個の固定サンプルを持ち、実行時は `t*7` の整数部を左番号、小数部を補間率として隣を lerp する。可変長キーの区間を毎回探索する代わりに、一定サイズの配列から評価できる。これが **curve baking**。

利点は実行時データが小さく規則的なこと。欠点は8サンプル間隔より鋭いピークを失いやすいこと。編集用のキーが多いから実行結果も同じ精度とは限らない。なお GPU Config は開始・中間・終了値も使っており、この固定8サンプル型を全エフェクトが必ず使うわけではない。どの型へ書き出しているかを実行側で確認する。

## 9. シークの方式を見分ける

| 対象 | 現行の手段 | 精度上の意味 |
| --- | --- | --- |
| Float Curve | 時刻から値を直接評価 | 同じキーと時刻なら同じ評価。 |
| Sequencer | 先頭からCPU更新を進めてイベントを発火 | 途中の副作用も起こしうる。 |
| CPU Particle / Mesh | 専用の更新を順に呼ぶ | 初期状態と乱数等の条件に依存。 |
| GPU Particle | 時計と要求を蓄積し、Draw時に年齢で近似 | 過去の衝突・Field等の完全再現ではない。 |

画面上で同じスライダーでも、その裏側は異なる。[GPU 詳細](04A_GPUパーティクルのメモリと計算.md)と照らし合わせ、プレビューで何を確認できたかを正しく判断する。
