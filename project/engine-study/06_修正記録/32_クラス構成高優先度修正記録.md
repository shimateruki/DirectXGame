修正日: 2026-10-13

対象: [31_クラス構成と責務境界の事前調査.md](../05_調査と整理/31_クラス構成と責務境界の事前調査.md) の高優先度1〜4

## まず、シーンJSONとC++クラスはどうつながるか

```text
Resources/json/3Dobject/stage1.json
  ├─ _sceneAsset.id = "stage1"           ← 配置データを識別するID
  └─ _sceneAsset.runtimeScene = "GAMEPLAY" ← 実行シーンの登録名
                 │
                 ▼
SceneManager が登録名を使って SceneFactory::CreateScene("GAMEPLAY")
                 │
                 ▼
RegisterGameScenes の "GAMEPLAY" → GamePlayScene 生成関数
                 │
                 ▼
GamePlayScene に stage1 の配置・設定JSONを読み込む
```

`stage1`、`stage2`、`stage3` はいずれも `runtimeScene = "GAMEPLAY"`。つまりステージごとにC++のシーンクラスがあるわけではなく、**同じ `GamePlayScene` に別の配置JSONを与える**構成である。既存の `GAMEPLAY` を使うScene Assetを増やすだけならC++の登録追加は不要。別のC++シーンクラスを作るときだけ、新しい登録名と生成関数を `RegisterGameScenes` に追加し、Scene Assetの「実行クラス」にその登録名を指定する。

エディターの「実行クラス」候補は登録一覧から表示される。JSONの文字列をC++の型名から自動探索する仕組みではない。UnityのScene Assetとスクリプト参照に似た見方はできるが、このプロジェクトではScene Assetの `runtimeScene` が**シーン全体の実行クラスを1つ選ぶキー**である。`ISceneController` を使う場合は、共有 `GAMEPLAY` の中の固有処理を別途選ぶ。

## 1. ゲーム固有シーンの登録場所

- `SceneFactory` は「名前→生成関数」の登録と生成だけを担当するようにした。エンジン側の `SceneFactory.cpp` から9個のゲームシーンクラスへの直接依存を外した。
- 登録一覧はゲーム側の `game/scene/RegisterGameScenes.h` に置き、起動時に `Game.cpp` が呼ぶ。既存の登録名・順序は維持したため、JSONとエディター候補の対応は変わらない。
- なお、現行の `Game.cpp` は起動処理の中心としてゲーム固有の登録を呼ぶ。アプリ起動部まで完全にエンジンから分離する改造は今回の対象外。

## 2. `BaseScene` が `Player` を知っていた理由と修正

修正前は `BaseScene` が `GetPlayer` / `SetPlayer` / `GetGameRule` を持ち、`Player` がオブジェクト一覧にいない場合だけ固定更新を追加で実行し、カメラ情報も別経路で更新していた。ゲーム側のローダーや敵・ギミックからの参照口にもなっていた。これは**所有者だから持っていた**というより、ゲーム専用の便宜的な窓口と例外処理が基底に混ざった状態だった。

- ゲーム用の参照口を `game/system/SceneGameplayAccess.h` の `ISceneGameplayAccess` へ移した。必要なシーンだけ実装し、ゲーム側の呼び出し元はこの能力を介して `Player` / `GameRule` を参照する。
- `BaseScene` の固定更新とカメラ反映はオブジェクト一覧を一度処理する形へ整理した。通常ロードの `Player` と王冠演出プレビューのコピーは一覧へ登録される経路を確認した。
- 敵の攻撃予告描画もゲーム側の `GameSceneDrawing.h` へ移した。各シーン内の呼び出し位置は維持した。
- `BaseScene` の一人称描画除外には、ゲーム専用の `Player*` ではなく汎用の `Object3d*` を渡す。

`ISceneGameplayAccess` のポインターは参照であり、`Player` の所有権を移さない。実際のオブジェクト所有は従来どおりシーンのオブジェクト管理側にある。

## 3. 設定画面とウィンドウ基盤

`WinApp` が `SettingsMenuOverlay` を直接参照してカーソル中央寄せを止めていた依存を外した。`WinApp` は汎用の「カーソル中央寄せ抑止」状態を持ち、設定画面の開閉側がその状態を更新する。複数の設定画面は既存の `activeCount_` を使って判定し、リプレイ状態の復元時にも同期する。

ショートカット抑止など、設定画面固有の判断はこのカーソル状態と混ぜていない。今後別の画面も同じ抑止を同時に要求するなら、要求元ごとの取得・解放方式へ拡張する必要がある。

## 4. イベント購読の個別解除

認識どおり、`Subscribe` が購読IDを返し、`Unsubscribe(id)` でその購読だけを解除できるようにした。`GameRule` と `GimmickBlinkBlock` は自分のIDを保持し、再初期化前と破棄時に解除する。攻撃ライフサイクルの検証プローブも終了時に自分の購読を解除する。シーン初期化時の `ClearAllListeners()` 呼び出しは削除し、別の購読を巻き込まないようにした。

配信中に解除しても走査中の要素を即時削除せず、無効化して配信終了後に整理する。配信中に追加した購読は次のイベントから通知する。`ClearAllListeners()` はAPIとして残るが、通常のシーン遷移には使わない。
