# 1. ゲームループとエディター基盤

## 1-1. まず全体の流れ

`main` から [`Framework::Run`](../../engine/core/Framework.cpp) へ入り、派生クラス [`Game`](../../engine/core/Game.cpp) の初期化・更新・描画を繰り返します。1フレームは大まかに「OS入力を受ける → ゲームとエディターを更新する → シーンを描く → エディター UI を重ねる → GPUへコマンドを提出する」です。`Game::Update` と `Game::Draw` を交互に追うと、責務の境界が見えます。

```text
Framework::Run
  ├─ Game::Initialize
  │   ├─ Engine services / Scene / PostEffect
  │   └─ Editor tools（USE_IMGUI 時）
  ├─ Game::Update
  │   ├─ 入力とシーン・エフェクトの更新
  │   ├─ 固定時間更新
  │   └─ エディターの操作とツール更新
  └─ Game::Draw
      ├─ Render Texture・Shadow・3D・2D
      ├─ PostEffect
      └─ Back Buffer・ImGui
```

## 1-2. 何を毎フレーム更新するのか

[`Game::Update`](../../engine/core/Game.cpp) は `deltaTime` を各システムに渡します。`Game::RunFixedUpdates` には経過時間を蓄積して 1/60 秒ごとに呼び出す仕組みがあります。ただし現行の `Object3d::FixedUpdate` は空で、移動・衝突全体が固定更新へ移されているわけではありません。通常の Scene Update も別途呼ばれます。[時計の詳細章](08B_時計と入力と音声の寿命.md)で、蓄積の上限とシステムごとの時間の違いを説明します。

`SceneManager` は現在シーン、次シーン、ロード中シーン、遷移段階を持ちます。[`SceneManager::ChangeScene`](../../engine/system/scene/SceneManager.cpp) と `ChangeSceneWithoutLoading` は同じ「画面切替」でもロード画面と暗転の扱いが違います。[`ScenePreloader`](../../engine/system/scene/ScenePreloader.cpp) は準備処理を分離し、準備後にメインスレッド側でシーンを差し替えます。**シーンを要求した瞬間に現在シーンのポインタが切り替わるわけではありません。** CPU の作業スレッド、Copy Queue と Fence、段階的初期化の現行構成は[ロードとシーン遷移の技術](30_ロードとシーン遷移の技術.md)で追います。

## 1-3. エディターの入口

エディター全体の入口は [`GameEditorController`](../../engine/core/editor/GameEditorController.cpp) です。`BeginFrame` で ImGui と ImGuizmo のフレームを開始し、`UpdateTools` が各専用ツールを更新し、`DrawToolWindows` がウィンドウを描きます。Scene/Hierarchy/Inspector などの共通操作は [`DebugEditor`](../../engine/utility/SystemDebug/editor/core/DebugEditor.h) が受け持ちます。ビルド条件は `USE_IMGUI` です。

`ImGui` は「そのフレームに必要な UI をコードから再生成する」即時モード UI です。ボタンを押したら直接ゲームデータを書き換える画面もありますが、エディター状態だけを変える画面もあります。このため UI の `DrawImGui` だけを読まず、変更先のオブジェクト、保存関数、実行時の読み込み関数まで辿る必要があります。

`ImGuizmo` は Scene View の移動・回転・拡縮ハンドルです。Hierarchy の選択、Inspector の値、Gizmo の操作が同じ Object を指すように `DebugEditor` が仲介します。[`EditorTransactionManager`](../../engine/utility/SystemDebug/editor/core/EditorTransactionManager.cpp) は連続ドラッグを一つの Undo 履歴にまとめます。

## 1-4. Game View と Play

エディターの Game View は [`GameEditorController::DrawGameView`](../../engine/core/editor/GameEditorController.Viewport.cpp) と [`Game::DrawEditorFrame`](../../engine/core/Game.cpp) の経路です。ゲーム画面を Render Texture へ描き、その結果をエディター UI に表示します。ウィンドウ内の表示倍率やマウス位置の換算はゲーム内部のワールド座標とは別です。

Play へ入る前後は編集シーンの復元が必要です。`ReplayDebugger` の Play スナップショットと `PlayModeChangeTracker` の「実行中に行った一部変更を選んで持ち帰る」機能は目的が異なります。**Playで見えた状態がそのまま保存済みシーンになるわけではありません。**

## 1-5. なぜこの分け方なのか

`Framework` は OS とループ、`Game` はゲーム全体の組み立て、`SceneManager` はシーン寿命、`GameEditorController` は編集画面、`DebugEditor` は編集対象と操作を受け持ちます。最初から一つの巨大クラスで追うと、描画順と保存順を混同しやすくなります。変更したい機能の入口から、データの所有者へ下りる読み方が有効です。

別の設計として ECS や Render Graph を中心に組む方法もあります。現行の CG2 は主に `Object3d` と各 Manager、明示的な描画順で構成されています。この資料では現行構造を先に理解し、代替設計は比較として扱います。
