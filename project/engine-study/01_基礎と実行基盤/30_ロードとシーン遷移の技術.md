# ロード画面とシーン遷移を、CPU・GPU・データの流れから読む

[総合目次](../00_目次と読み方.md) / [技術解説](../資料案内_技術解説.md)

更新日: 2026-10-12。対象はロード画面を挟む `SceneManager::ChangeScene` の経路です。初回起動や `ChangeSceneWithoutLoading` は下の「適用範囲」で区別します。用語だけでなく、何をどのスレッドで実行し、何を待つために画面が止まるのかをコードに沿って説明します。

## 1. 全体像

```text
遷移要求
  ↓ Fade で旧シーンを暗転
旧シーンの GPU 使用完了を待つ → 旧シーンを破棄 → LoadingScene を表示
  ↓
SceneLoadManifest を作る
  ↓ std::async: 作業スレッド
JSON の依存探索・画像のデコード・モデルの準備・音声の準備
  ↓ std::future の完了を毎フレーム確認
画像とモデルの作成を別の作業スレッドで進める
  ↓ Copy Queue へ画像転送を提出し、Fence を毎フレーム確認
メインスレッドで次シーンの InitializeLoadingStep を小分けに実行
  ↓ 初期化と転送完了、最低表示時間、暗転を確認
LoadingScene の GPU 使用完了を待つ → 次シーンへ交換 → OnActivated
```

この流れの司令塔は [`SceneManager`](../../engine/system/scene/SceneManager.cpp) です。`currentScene_` が表示中のシーン、`preparedScene_` が準備中の次シーンです。ロード中は `currentScene_` に [`LoadingScene`](../../engine/system/scene/LoadingScene.cpp) が入り、旧シーンのオブジェクトは既に破棄されています。

| 技術 | この実装での役割 | 誤解しやすい点 |
| --- | --- | --- |
| `std::async` / `std::future` | 依存解析と素材準備、次の段階の素材作成を作業スレッドで進める | シーンの全初期化が別スレッドになったわけではない |
| COM のスレッド初期化 | 作業スレッドで画像処理などを使う前に `CoInitializeEx` を呼ぶ | メインスレッドの COM 初期化を自動で引き継ぐわけではない |
| D3D12 Copy Queue | テクスチャの転送コマンドを描画用コマンドとは別のキューへ提出する | 転送の前後に必要な CPU 側の作成まで消えるわけではない |
| Fence | GPU が提出済みの転送を終えたか確認する | GPU の処理時間と CPU が待たされた時間は別の値 |
| 段階的初期化 | 描画パイプライン、粒子、配置物などをフレーム間に分散する | 一段階の中の重い処理はそのフレームを止める |
| プロセス内キャッシュ | 同じシェーダーの再コンパイルを抑える | アプリ再起動後まで永続化するものではない |

## 2. 遷移の入口とロード画面

[`SceneManager::Update`](../../engine/system/scene/SceneManager.cpp) は `Idle` → `FadingOutCurrent` → `Loading` → `FadingOutLoading` と進みます。暗転後の `BeginLoadingTransition` では、旧シーンが使っていた GPU 資源を破棄する前に、画像の転送バッチと `DirectXCommon::WaitForGPUAndReset` の完了を待ちます。これは安全な寿命管理のための同期です。そこで `Finalize` して [`LoadingScene`](../../engine/system/scene/LoadingScene.cpp) を作り、進捗 8% から表示を始めます。

LoadingScene は 3D の描画をせず、背景・ヒント・スライム・進捗ゲージを Sprite で描きます。`targetProgress_` は実処理の進捗、`displayedProgress_` はそれを滑らかに追う表示値です。ゲージのアニメーションが動くかどうかは、メインスレッドが次のフレームまで戻れるかに依存します。重い一関数が更新を占有すれば、作業スレッドが存在しても絵は一時停止します。

## 3. 依存を集める作業スレッド

次シーンの [`BuildAsyncLoadManifest`](../../engine/system/scene/BaseScene.h) がレイアウト JSON、追加 JSON、モデル、テクスチャ、音声を列挙します。[`ScenePreloader::Prepare`](../../engine/system/scene/ScenePreloader.cpp) は分割された配置 JSON を展開し、各 JSON に書かれた参照をさらに辿ります。追加の JSON が見つかれば処理件数も増やします。見つからない依存は警告に残します。

このスレッドでは JSON を解析して `ScenePreloadData::jsonDocuments` に保持し、`TextureManager::Prepare`、`ModelManager::PrepareModel`、`AudioPlayer::LoadSoundFile` を呼びます。画像の事前デコードやモデルの CPU 側準備が主眼です。`SceneManager` は `future.wait_for(0)` で完了だけを調べ、まだ終わっていなければ LoadingScene を更新・描画するフレームへ戻ります。`std::atomic` の件数と `mutex` で保護された処理名を使う [`ScenePreloadProgress`](../../engine/system/scene/ScenePreloader.h) は、作業スレッドと表示側の間で進捗を共有します。

依存解析後は [`SceneManager::StartPreparedAssetsAsync`](../../engine/system/scene/SceneManager.cpp) がもう一つの `std::async` を開始し、テクスチャ `Load` とモデル `LoadModel` を進めます。二つの Future は**連続する段階**であり、シーン全体を一度に並列生成しているわけではありません。画像の転送記録が可能な期間は `TextureManager::SetAsyncUploadRecording` でスレッドごとに制御します。メインスレッドは素材作成完了を非ブロッキングで確認します。

## 4. GPU への画像転送と Fence

[`TextureManager::BeginAsyncUploadBatch`](../../engine/graphics/core/TextureManager.cpp) は D3D12 の Copy Command Allocator、Copy Command List、Copy Queue 用 Fence を使ったバッチを開始します。画像をアップロードするときは、中間リソースを `asyncTextureUploads_` に保持して転送コマンドを記録します。`SubmitAsyncUploadBatch` はコマンドを提出し、Fence 値を Signal します。`PollAsyncUploadBatch` は完了値を読むだけで、未完了なら次のフレームへ戻します。完了を確認してから中間リソースを解放します。

この設計はロード中の転送待ちを毎フレームの確認へ置き換えます。ただし、バッチを開始できない場合や同期が必要な呼び出しでは従来の待機経路があり、シーン交換の直前には GPU が旧資源を使い終えたことを必ず確認します。Copy Queue を使ったことだけで「GPU 待ちがゼロ」とは言えません。`Poll` は待たない、`WaitForAsyncUploadBatch` は必要な場合に待つ、という違いが重要です。

## 5. シーン本体をメインスレッドで段階的に作る

画像とモデルの準備後、[`SceneManager::PrepareLoadedSceneOnMainThread`](../../engine/system/scene/SceneManager.cpp) が次シーンの `BeginLoadingInitialize` を呼び、毎フレーム `InitializeLoadingStep` を一度進めます。Scene の初期化には CameraManager、LightManager、描画管理など共有状態の変更があるため、メインスレッドで行います。標準の [`BaseScene`](../../engine/system/scene/BaseScene.cpp) は従来の `Initialize()` を一回呼ぶだけです。つまり、この分割の恩恵は **段階的な実装を持つ Scene** に限られます。

[`GamePlayScene`](../../game/scene/gameplay/GamePlayScene.Setup.cpp) では、描画共通部品、Object 系、GPU 粒子、Mesh Effect、Debris、VFX、Skybox、ステージ配置物、Sprite、HUD、Overlay、Controller、ゴール演出などをフェーズ順に作ります。GPU 粒子プリセットなどは一種類ずつ進めます。前のフェーズで必要な資源を作ってから次へ進むため、単にループを任意の場所で切った構造ではありません。

3D 描画の [`Object3dCommon::InitializeStep`](../../engine/graphics/3d/object/Object3dCommon.cpp) は Root Signature と各種 PSO の作成を 24 段階に分けます。Root Signature を先に用意し、対応するパイプラインを後で作る順番を維持します。これは「24 フレームで必ず完了」という時間保証ではありません。各段階の DXC コンパイルや PSO 生成が重ければ、そのフレームはまだ長くなります。

配置物は [`LevelLoader::BeginObjectLayoutLoad` / `ContinueObjectLayoutLoad`](../../game/system/LevelLoader.cpp) を使います。PresetManager と GameplayStatusManager の初期化を別段階に置き、`_player`、`_enemy`、`_object`、`_camera` の分割 JSON、または旧単一 JSON を読みます。ゲームプレイのロードでは `ContinueObjectLayoutLoad(this, 4)` を呼ぶため、一フレームの生成上限は 4 件です。全件生成後に親子参照を GUID 優先で解決し、敵のシーン参照も結びます。`LoadObjectLayout` の同期 API は互換性のため残り、内部で完了まで同じ処理を繰り返します。

## 6. DXC のキャッシュは何を省くか

[`DirectXCommon::CompileShader`](../../engine/graphics/core/DirectXCommon.cpp) はシェーダーのファイルパス、プロファイル、エントリーポイントをキーに、DXC が出したバイトコードをプロセス内で再利用します。元ファイルと `#include` 先の更新時刻が変われば再コンパイルします。依存先を追跡できない場合はキャッシュしません。[`GPUParticleSystem`](../../engine/graphics/particle/GPUParticleSystem.cpp) にも Compute Shader 用の共有バイトコードキャッシュがあります。

これで同じシェーダーをシーンや粒子システムごとに繰り返しコンパイルする CPU 負荷を減らします。ただし、GPU のバッファ、Descriptor、PSO を作る処理まで共有するわけではありません。DXC の結果はメモリ内だけなので、アプリを再起動した直後は再びコンパイルが必要です。テクスチャの DDS キャッシュとは別の仕組みです。

## 7. 進捗バーと実時間の関係

[`CalculateLoadingProgress`](../../engine/system/scene/SceneManager.cpp) は、Manifest と事前準備を 8～60%、素材作成を 60～96%、シーン初期化を 96～98.5% へ写します。GPU 転送待ちには 97% または 99% を表示し、すべての準備が済むと 100% になります。最低表示時間は 0.45 秒です。

これは「各フェーズの作業件数」を帯へ写した表示で、残り秒数の予測ではありません。たとえば大きな PSO 作成が一段階に含まれると、進捗はあまり動かずフレームだけ長くなります。LoadingScene は表示値を補間するので、実処理が済んだ瞬間に画面上の長さが一致するとも限りません。

## 8. 直近の計測で分かったことと、まだ残ること

ゲーム内ステータスに見えた「CPU 約 592 ms」は、更新処理に CPU が要した時間の表示です。これだけで GPU 待ちが主因とは判定できません。[`Game::RecordDrawProfile`](../../engine/core/Game.cpp) の「GPU待機」欄も、描画合計から命令発行時間を引いた残差であり、GPU が実際に演算した時間そのものではありません。GPU 要因と断定するには Fence・Present の待機ログや GPU タイムスタンプを突き合わせます。

2026-10-12 の Development x64 で、`TITLE → GAMEPLAY → PREVIEW → GAMEPLAY → GAMEPLAY` を通す描画付きの検証を行いました。変更前には GAMEPLAY の一初期化段階が約 1.37～1.44 秒、PREVIEW の初期化が約 1.70 秒でした。段階化・キャッシュ・転送見直し後の同じ検証では、GAMEPLAY の最大初期化段階は約 149 ms、PREVIEW は約 221 ms でした。GPU 同期待ちはその検証で約 44～45 ms の例があり、観測した最大の停止は主に CPU 側の初期化でした。これは測定した遷移での結果であり、全ステージ・全 PC の主因を断定するものではありません。

残った 149 ms はゴール演出タイムラインの初期化、PREVIEW の 221 ms は同シーンの初期化段階です。PresetManager の初期化にも約 63～72 ms の例があります。分割後も一段階の関数が 16.7 ms の 60 FPS 予算を超えるため、完全に無停止にはなっていません。次に改善するなら、下の計測で**最も長い段階を特定し、その内部をさらに分割または事前準備する**のが筋です。ゲームルールの依存順や GPU 資源の寿命を保たずに全初期化を作業スレッドへ送る方法は、このコードには適しません。

## 9. 自分で再計測する手順

[`LoadingProfiler`](../../engine/system/scene/LoadingProfiler.h) は渡された処理時間が 16 ms 以上なら `[LoadingProfile]` として Visual Studio のデバッグ出力へ書きます。`CG2_LOADING_PROFILE_LOG` にファイルパスを設定すると、同じ行をファイルにも追加します。`SceneManager` の段階、`LevelLoader` の準備、画像転送待ち、DirectXCommon の Present・GPU 同期などの行を比較します。なお、[`DirectXCommon::PostDraw`](../../engine/graphics/core/DirectXCommon.cpp) 側は Present とフレーム Fence 待ちが **40 ms 以上**のときに記録関数を呼びます。ログに行がないことは、待ちがゼロだった証拠ではありません。計測用ログの出力先は、生成物として管理している作業用フォルダーなど、既存データを上書きしない場所にしてください。

1. Development x64 で起動し、確認したい遷移を一つずつ再現する。
2. `InitializeLoadingStep progress=...` の最大値を見て、どの進捗帯で止まったか調べる。
3. 同じ時刻の `async texture upload GPU wait`、`old/loading scene GPU synchronization`、`DirectXCommon Present` を比較する。
4. 現象が再現する PC とシーンで、初回起動と二回目を分けて測る。プロセス内シェーダーキャッシュが効く二回目は条件が違う。
5. 変更後は画面の動きと実際の Play 遷移を確認する。ビルド成功やログだけを目視確認の代わりにしない。

開発用の [`SceneTransitionRuntimeProbe`](../../tests/SceneTransitionRuntimeProbe.h) は、環境変数 `CG2_SCENE_TRANSITION_TEST_LOG` があるときだけ実遷移と描画を通し、一定フレーム後に次へ進む回帰用経路です。直近の検証はこの経路で完走しました。これはマウスやコントローラーによる手動操作、全ステージの体感、ロード中の全演出の見え方まで保証しません。

## 10. 適用範囲と寿命上の注意

初回起動は [`SceneManager::Initialize`](../../engine/system/scene/SceneManager.cpp) が最初の Scene を直接初期化するため、ロード画面を通りません。死亡復帰などの `ChangeSceneWithoutLoading` も直接 `Initialize()` する経路で、上記の段階的ロードとは別です。従って「どの切り替えも同じように滑らか」とは言えません。

終了時とシーン交換時は、作業スレッドの Future、Copy Queue の転送、描画 GPU の使用を必要な順序で待ちます。解放済み Scene の `Object3dCommon` を常駐 Mesh Effect が参照しないよう、旧シーンの演出を先に消します。効果の寿命については[14J シーン遷移時のエフェクト寿命](../04_攻撃制作/14J_シーン遷移時のエフェクト寿命と実行検証.md)も参照してください。
