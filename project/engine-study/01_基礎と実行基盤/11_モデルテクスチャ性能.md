# モデル、テクスチャ、性能計測

詳細解説：[骨階層・LBS・Compute Skinning の詳細](../02_描画と演出/07A_骨の補間とAnimatorの状態遷移.md)。

[目次](../00_目次と読み方.md)へ。3D ファイルを指定した後に画面に出るまで、そして重くなったときにどこを計測するかを説明する。

## モデルファイルから描画データへ

[`ModelManager`](../../engine/graphics/3d/model/ModelManager.cpp) は名前からモデルを探し、`.obj`、`.gltf`、`.glb` 等を扱う。実際のファイル解析は [`Model.Loader.cpp`](../../engine/graphics/3d/model/Model.Loader.cpp) にあり、**Assimp** の Importer で Scene、Mesh、Material、Node、Animation を取り出す。Assimp は異なる3Dファイル形式を共通のデータ構造へ変換するライブラリ。Model はその結果をエンジン用の頂点・インデックス・材質・骨・アニメーションへ写す。ファイル拡張子を見つけたことと、GPU が描けるバッファができたことは別段階。

モデルは Mesh ごとの頂点・インデックスを持つ。頂点には位置だけでなく法線、UV、骨番号・重みなどが必要になる場合がある。**法線**は光の当たり方、**UV**はテクスチャ上の位置、**インデックス**は頂点を再利用して三角形を作る順番。描画時は [`MeshRenderer`](../../engine/graphics/3d/MeshRenderer.cpp) が適切な材質、パイプライン、バッファを選んで命令を出す。Model Manager は資産の発見・再利用、Renderer は描画の実行という役割分担。

## スケルトン、アニメーション、Compute Skinning

骨付きモデルは、Node の階層を Joint の配列へ変換し、骨に「どの頂点へ何割影響するか」という重みを持つ。[`Model.Skeleton.cpp`](../../engine/graphics/3d/model/Model.Skeleton.cpp) は姿勢を更新し、ジョイント行列を作る。一般に各頂点の変形は「骨ごとの変換結果 × 重み」を足したもの。これが**スキニング**。動くのはモデル全体の Transform だけではなく、頂点の位置そのもの。

[`Model.Animation.cpp`](../../engine/graphics/3d/model/Model.Animation.cpp) は時刻から移動・回転・拡縮のキーを評価する。回転は Quaternion の `Slerp` を使い、二つの姿勢のブレンドにもつながる。[`ModelCommon`](../../engine/graphics/3d/model/ModelCommon.cpp) は `Skinning.CS.hlsl` 用の Compute Pipeline を作り、対応可能なモデルは Compute Skinning を使用する。Compute Shader が変形済み頂点バッファへ書き、後段の描画がそれを読む。使用可否の分岐があるため、**全モデルが必ず Compute Skinning**とは書かない。使えないケースの描画経路は `Model::UsesComputeSkinning` と Renderer 側の選択を確認する。

## Texture Manager と DDS キャッシュ

[`TextureManager`](../../engine/graphics/core/TextureManager.cpp) は画像ファイルを読み、D3D12 リソースと SRV 番号へ結び付ける。**SRV** はシェーダーがテクスチャを読み取るためのビュー。ロードしただけの CPU 側画像を Pixel Shader が直接読むわけではない。GPU メモリへ転送する Upload Resource、Copy Command、Fence の関係を理解すると、非同期ロード中に未完成の画像を参照してはいけない理由が分かる。

この実装には **DDS キャッシュ**がある。読込時間が一定以上の元画像を対象に JSONL の変換要求を出し、次回以降の読込負荷を下げる。法線マップ等の線形テクスチャと色テクスチャでは変換形式を分ける。キャッシュは元画像の内容そのものではなく、再生成可能な派生物。エディターの一時 Preview 画像には不要なキャッシュ生成を避ける条件がある。[`AssetDatabase.DDSCache`](../../engine/utility/SystemDebug/editor/core/AssetDatabase.DDSCache.cpp) はエディター側の索引・管理に関わる。画質や色が不自然なら、元画像、DDS の新旧、線形 / sRGB の扱いを確認する。

## LOD と描画回数

[`MeshRenderer.Lod.cpp`](../../engine/graphics/3d/MeshRenderer.Lod.cpp) は距離などに応じてモデルの詳細度を切り替える経路。LOD は遠い物体の頂点数を減らすが、描画命令の回数まで必ず減るとは限らない。また切替距離が不適切なら見た目の急変が目立つ。[`ModelOptimizerWindow`](../../engine/utility/SystemDebug/editor/windows/ModelOptimizerWindow.cpp) で段階を比較してから実シーンの距離とカメラで確認する。

## 計測してから最適化する

[`RenderStats`](../../engine/graphics/core/RenderStats.cpp) は Pass ごとの Draw、Indirect Draw、Compute Dispatch、粒子、ライト、Post Process 等を数える。[`ProfilerManager`](../../engine/utility/SystemDebug/ProfilerManager.cpp) は CPU / GPU 時間やロード時間を記録し、`PROFILE_SCOPE` は範囲の CPU 所要時間を取る。これらは「何が多いか」「どこが長いか」の手掛かり。Draw 回数が多いだけで GPU が遅いとは確定しないし、CPU 時間の長さだけで Pixel Shader の重さも分からない。原因は同じ場面・同じ設定で測り、数値と画面をセットで比較する。

[`D3DResouceLeakChecKer`](../../engine/utility/SystemDebug/D3DResouceLeakChecKer.cpp) は DXGI のデバッグインターフェースが使える環境で、終了時に生存リソースを報告する。これは性能測定とは別で、GPU リソースの解放漏れを調べるための道具。

## 具体的な読み順

`ModelManager` の名前解決 → `Model.Loader` の Assimp 変換 → `Model` の CPU/GPU データ → `Object3d` の Transform・材質 → `MeshRenderer` の Pass 選択 → HLSL → RenderStats。アニメーションがあれば途中に Animation / Skeleton / Compute Skinning を挟む。これで「モデルが出ない」「動かない」「重い」を別々に調べられる。
