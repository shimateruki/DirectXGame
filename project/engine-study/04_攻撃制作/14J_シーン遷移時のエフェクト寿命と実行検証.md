# シーン遷移時のエフェクト寿命と実行検証

## 発生した問題

ゲームシーンへ移動した直後、`MeshEffectManager::Draw()`から呼び出した`EffectObject3d::Draw()`でアクセス違反が発生しました。

実行ファイルをCDBデバッガーで動かし、タイトルに長寿命のメッシュエフェクトを置いてからGAMEPLAYへ移動すると再現しました。タイトルは120フレーム描画でき、ゲームシーンへの遷移後、次の呼び出し履歴で停止しました。

```text
Object3dCommon::SetEffectGraphicsCommand
EffectObject3d::Draw
MeshEffectManager::Draw
Game::DrawSceneToRenderTexture
Game::DrawEditorFrame
Game::Draw
Framework::Run
```

例外コードは`0xC0000005`です。報告画像の描画経路と一致します。停止位置には差があり、採取した実行では描画コマンド取得後のパイプライン設定で停止しました。

## 所有権と寿命が合っていなかった

`Object3dCommon`はSceneが所有する描画基盤です。`EffectObject3d`と内部の`MeshRenderer`は、初期化時に渡された基盤への非所有ポインタを保持します。

一方、`MeshEffectManager`はSceneをまたいで残る常駐管理クラスです。修正前の`Initialize()`は管理側の`common_`を書き換えるだけで、既存エフェクトが持つ古い参照は更新しませんでした。タイトルやプレビューSceneの終了時にはメッシュエフェクトを消さない経路もあり、Sceneの描画基盤だけが先に破棄されていました。

```text
旧SceneがObject3dCommonを破棄
  ↓
常駐Managerには旧SceneのEffectObject3dが残る
  ↓
新Sceneの最初の描画で、旧Sceneの基盤を参照
  ↓
アクセス違反
```

これは解放済み参照、いわゆるdangling pointer／use-after-freeの問題です。参照しているアドレスがnullでなくても、所有者の寿命が終わっていれば安全には使えません。

## 修正した処理

### SceneManagerで破棄順を統一

`ReleaseSceneMeshEffects()`を追加し、GPU待機が完了した後、Sceneの`Finalize()`より前にメッシュエフェクトを解除します。ロード画面へ入る経路、ロード画面なしの切替、終了処理、初回初期化の失敗処理に適用しています。

```text
GPU処理完了を待つ
  → エフェクトの外部登録を解除
  → エフェクトを破棄
  → SceneのFinalize
  → Object3dCommonを破棄
```

LoadingSceneはObject3dCommonを持たないので、この解除は行いません。ロード中に準備した次Sceneのエフェクトまで、LoadingSceneの終了で消してしまうことを防ぎます。

### MeshEffectManager側も寿命を揃える

`Initialize()`で別の描画基盤が渡されたときは、旧エフェクトを解除してから差し替えます。Sceneの明示的な破棄処理と組み合わせ、アロケータが同じアドレスを再利用する場合にも対応します。

`ClearActiveEffects()`では、所有しているエフェクトをCollisionManagerから外し、デバッグ用参照・スコープ・配置オフセットも解除してから本体を破棄します。編集で当たり判定フラグをOFFにした場合も、過去の登録を残さないよう解除します。未登録Objectの解除はCollisionManager側で安全に扱います。

`Clear()`はこの共通処理を使った上で、プリロード済み印と生成元の参照も解除します。攻撃配置などの「再生中のものだけ消す」と、シーン切替の「生成基盤も手放す」を区別しています。

## 実行検証の仕組み

`tests/SceneTransitionRuntimeProbe.h`は、環境変数`CG2_SCENE_TRANSITION_TEST_LOG`を指定したDevelopment／Debug実行だけで動く回帰確認です。通常の起動では何もしません。

Gameの通常の更新と描画を使い、`Game::Draw()`の終了後にフレーム数を記録します。各Sceneに120秒の寿命を持つメッシュエフェクトを生成し、次の順で各120フレームを描画します。

1. TITLE
2. GAMEPLAY
3. PREVIEW
4. GAMEPLAY
5. GAMEPLAYをロード画面なしで再読み込み

次Sceneへ古い検証用エフェクトが残っていないことも確認します。最後は通常の終了処理へ進みます。モック描画やJSONだけの検証ではなく、DirectX 12の描画を実行するテストです。

実行例:

```powershell
./tests/RunSceneTransitionRuntimeProbe.ps1 -Debugger -TimeoutSeconds 600
```

スクリプトは既にゲームが動いていれば中止し、他のゲームプロセスを終了しません。起動設定`user_config.json`は実行前のバイト列を保持し、終了後に復元します。テストログはTEMPへ出し、明示的なPASSと正常終了の両方を確認します。CDBを使う場合はアクセス違反で呼び出し履歴を採取します。

この検証はシーン遷移と実描画の寿命を確認するものです。ギズモの手触りやエフェクトの美術的な見え方、全攻撃の命中結果を検証するものではありません。

## 修正版の実行結果

Development x64の実行ファイルをCDB下で実行し、TITLE → GAMEPLAY → PREVIEW → GAMEPLAY → GAMEPLAYの直接再読み込みを確認しました。各区間120フレーム、合計600フレームの描画に成功しています。Scene世代は順に1・3・5・7・8でした。

旧エフェクトの持ち越し検査、通常の終了処理まで完了し、検証スクリプトの終了コードは0でした。デバッガーにアクセス違反・未処理のsecond chance例外の記録はありません。

修正前の記録はTEMPの`cg2-transition-before.log.debugger.txt`、成功した修正版の記録は`cg2-transition-verified.log`とその`.debugger.txt`です。検証時のゲームシーンは起動設定のstage1です。起動設定はテスト後に復元済みです。

最初の修正版実行は、複数の実アセット読込を合算する180秒制限に達して失敗扱いにしました。制限を各遷移180秒に分け、外側にも600秒の上限を設けて再実行したものが上記の成功結果です。

今回の実行確認はDevelopment構成です。Debug構成の全体ビルドや、マウスによるギズモ操作感の確認は含みません。
