# 全クラスのカプセル化調査

[目次](00_目次と読み方.md) / [型定義の一覧](16_全クラスコメント再点検.md)

`Object3d::transform_` など、下記で残課題としていた保護メンバーの修正結果は[カプセル化の修正記録](25_カプセル化の修正記録.md)を参照。この章の優先度表は調査時の記録として残す。

## 目的と判定基準

2026-10-09 時点の自作 C++ を対象に、クラスの内部状態を意図した操作以外で変更できる経路を調べた。対象は `engine`、`game`、`tools/TextPngTool` のヘッダーと実装。外部ライブラリ、生成物、提出用コピーは除く。型定義を探す際は既存の[全型一覧](16_全クラスコメント再点検.md)を索引にし、現行ソースの公開領域、可変参照・ポインタを返す API、`friend`、主要な呼び出し側を再確認した。

この調査でいうカプセル化は、**状態の所有者が変更手順・値の範囲・寿命・保存や Undo の整合性を守れるか**を指す。`public` な設定構造体や GPU 転送用構造体は、値を運ぶための型なので、それだけでは問題に数えない。C++ の同一プロセス内のアクセス制御は不正なプログラムを防ぐセキュリティ境界ではない。ここで挙げるのは設計上の整合性と保守性のリスクであり、外部からの攻撃経路を実証したものではない。

優先度は、現行コードで迂回が起きているか、壊せる不変条件が明確か、利用側が広いかで付けた。全型の全メソッドの動作証明ではなく、静的調査である。特に今後の修正では Editor の操作・Undo・保存・Play を同じ経路で確認する必要がある。

## 結論

最初に直す候補は、シーンの所有コンテナ、ライトの可変配列、`Object3d` の Transform である。これらはすでに利用側が直接変更しており、専用操作があるのに通っていない。次に、エフェクト・ポストエフェクト・VFX の実行状態と編集状態の境界を整理する。全クラスを一括で private 化すると Editor、ロード、Replay を壊すため、利用側を移す小さな単位で改良する。

## 高優先項目の修正状況（2026-10-09）

下の表は調査時の状態を記録している。今回、次の変更を行った。最終差分は Development / Debug x64 の両方でビルドとリンクが成功した。

| 項目 | 修正内容 | 残る確認 |
| --- | --- | --- |
| Scene の所有コンテナ | Scene と ObjectManager の公開 getter を読み取り専用にし、Manager を通す即時追加・取り出しと Sprite の追加・並び替え操作を設けた。直接 `push_back` していたロード・Editor・Replay を移した。Prefab 同期も Scene API を使い、新しい `friend` は設けていない。 | Editor で作成・削除・Undo・保存・Play、Replay 復元を実操作で確認する。 |
| LightManager のライト配列 | 公開 getter を読み取り専用にし、追加・更新・削除・全削除を Manager の操作へ集めた。LightEditor と読み込み処理を移した。 | Editor の追加・削除・保存・再読込と描画反映を実操作で確認する。 |
| Object3d の Transform | 公開 getter を読み取り専用にし、位置・スケール・Euler角・Quaternion・回転モード・外部アンカーの設定 API へ外部からの直接代入を移した。複数値の編集は `SetLocalTransform` でまとめる。 | `transform_` 自体は派生クラス向けの `protected` に残り、派生クラスから直接変更できる。Inspector の複数選択、ギズモ、親変更、ゲーム中の移動、保存・再読込、Replay で姿勢を確認する。 |

`GetTransform()` が返す `const Transform*` は参照先オブジェクトの寿命を越えて保持しない。`SetTransformAnchor` に渡す親 Transform も借用参照なので、呼び出し側が寿命を保証する。行列更新は従来どおり呼び出し側の更新タイミングで行う。これらの実操作はまだ検証していないため、ビルド成功だけで動作完了とは判定しない。

確認中、同時作業の [`CopyStyleHud.h`](../game/ui/CopyStyleHud.h) が更新途中の時点では C2589 が出た。その後、共有作業ツリーの更新を待って再ビルドした。通常の Development 出力先は `DirectXGame.exe` を開けず LNK1104 になったため、コードを変えずに生成先だけ分けて検証した。成功した出力先は `C:\二年前期\CG2\generated\outputs\EncapsulationCheck\` と `C:\二年前期\CG2\generated\outputs\EncapsulationCheckDebug\`。Editor・ゲーム内の実操作確認は未実施。

## 授業資料との照合（今回の３項目のみ）

参照資料: [SR1「01_01. カプセル化」](https://docs.google.com/presentation/d/1E9HJRK0354HP-hYghy6sDJxu742XtSoVUlVprKlJWMU/edit?slide=id.g388d2403e64_0_8#slide=id.g388d2403e64_0_8)。３枚目は状態と操作をまとめ、必要な入口だけを公開する原則を説明している。７枚目は無関係なクラスへの `friend` 公開、８枚目は内部コンテナの可変参照、９枚目は状態を触るためだけの `protected` 変数を問題例としている。

| 資料の観点 | 今回のコードでの確認 | 判断 |
| --- | --- | --- |
| 可変コンテナをそのまま返さない（８枚目） | Scene の `GetObjects/GetSprites`、`ObjectManager::GetObjects`、LightManager の点光源・スポットライト getter を `const` 参照にした。 | 外部から配列の追加・削除・並べ替えを直接行う経路を閉じた。 |
| `friend` で内部状態を開かない（７枚目） | Prefab 同期は Scene の追加・取り出し操作へ変更し、`BaseScene` に一時的に設けた `friend class DebugEditor` を削除した。 | 今回の３項目では新たな `friend` に依存しない。 |
| `protected` の状態を安易に増やさない（９枚目） | `LightManager` のライト配列は `private`。`BaseScene` には派生シーンが自分の Sprite 配列を返す `protected` の仮想操作があるが、所有配列そのものを基底の `protected` 変数にはしていない。一方 `Object3d::transform_` は既存の `protected` 変数で、派生クラスが直接変更している。 | Transform の公開 getter は閉じたが、派生クラス経由の迂回は残る。次は派生クラスの直接操作を Setter に移し、`transform_` を `private` にできるか検証する。ほかの `protected` 全般への変更は今回の範囲外。 |

## 問題扱いしなかった代表例

- [`GameDataManager`](../game/system/GameDataManager.h): `GetOrCreateStarCoins` は private。公開の `SetStarCoinCollected` が番号を確認し、変更時に `Save()` する。セーブ状態を外へ直接渡す設計ではない。`Save()` の成否など別の検討はあり得るが、この調査の「公開可変状態」には当てはまらない。
- [`GameSettingsManager`](../game/system/GameSettingsManager.h): 音量などは private で、Setter が範囲制限や即時反映を担当する。`Save()` との区別もコメントにある。
- [`SceneManager`](../engine/system/scene/SceneManager.h): 現在シーンは `unique_ptr` で private に保持し、遷移の段階も private。`GetCurrentScene()` の借用ポインタ自体より、派生シーンの所有コンテナが可変参照として公開される経路を優先した。
- [`Model`](../engine/graphics/3d/model/Model.h)、[`Sprite`](../engine/graphics/2d/Sprite.h)、[`Object3d`](../engine/graphics/3d/object/Object3d.h) 内の公開 `struct`: 多くはシリアライズ、頂点、GPU 定数、Replay の値型。公開フィールドだけを理由に隠すと用途を損なう。所有者の生きた状態へ可変参照として返す場合に再評価する。
- [`Player`](../game/actor/player/Player.h)、[`BaseEnemy`](../game/actor/enemy/core/BaseEnemy.h)、[`InputManager`](../engine/system/input/InputManager.h)、[`TextureManager`](../engine/graphics/core/TextureManager.h): 主要な実行状態・所有物は private または protected。protected は派生型が変更できるため、継承契約が崩れる箇所が見つかれば個別に調べる。

## 改良する順序と確認条件

1. **所有権から着手**: `BaseScene` に追加・削除・列挙の API を作り、LevelLoader、Editor、Replay、各 Scene の直接 `push_back` を順に移す。未対応の Scene に追加した際は黙って共有空配列へ入らないことを確認する。
2. **ライトの管理操作を統一**: 追加上限、初期値、全削除、個別編集を `LightManager` へ集める。Editor から追加・削除・保存・再読込して同じ内容が描画されることを確認する。
3. **Transform とカメラ設定の検証を所有者へ集める**: Editor のギズモ、親変更、ゲーム中の移動、保存・再読込、Replay 復元で姿勢が一致することを確認する。
4. **演出データは最後に分離**: VFX と PostEffect は使用箇所が広い。Preview と実ゲームの再生、途中停止、シーン遷移後の残留、Undo/保存を先に検証条件として固定してから変更する。

上の優先度表は修正前の静的調査記録であり、現在の公開 API を示すものではない。修正後の結果と未確認事項は「高優先項目の修正状況」に記載した。
