# 時計・入力・音声の寿命を追う

[目次](00_目次と読み方.md) / [ゲームループ](01_ゲームループとエディター基盤.md)

## 1. 一つのフレームにも複数の時間がある

入口は [`Game::Update`](../engine/core/Game.cpp)。`CalculateDeltaTime` は前回からの実時間を秒で得るが、0.1 秒より長い場合は 0.1 に制限するのではなく、1/60 秒へ置き換える。デバッガで長時間止めた後に、その全時間をゲームへ一度に渡すことを避ける処理である。したがってこの dt は厳密な壁時計の経過時間とは常に一致しない。

通常のゲーム用時間は次の積になる。

```text
finalDeltaTime = deltaTime × timeScale × feedbackTimeScale
```

Play でなければ基本値は 0。Replay 用の処理がさらに値を解決する。例えば dt=1/60、timeScale=0.5、feedbackTimeScale=0.2 ならゲームに渡るのは約 0.001667 秒である。

`VFXSequencer::UpdateFeedbackRuntime` はこの積を作る前に元の dt で更新される。ヒットストップの終了までゲーム用のゼロ時間で数えると永遠に終了しないため、停止を管理する時計と停止されるゲームの時計を分ける必要がある。

## 2. どの処理がどの時計を使うか

`UpdateGameSystems` の現行分岐は次のように読む。

| 処理 | 渡される時間の主な規則 |
| --- | --- |
| Scene の通常 Update | 通常は finalDeltaTime、遷移中は元の dt |
| 固定更新 | finalDeltaTime を蓄積、遷移・Replay 停止では蓄積を消す |
| GPU Particle / OneShot VFX | Play かつ Replay 停止でなければ finalDeltaTime |
| Debris | Replay 停止でなければ元の dt |
| Fade | Replay 停止でなければ元の dt、非同期初期化中は更新条件あり |
| PostEffect の time | Replay 停止でなければ元の dt |
| 振動・Feedback 管理 | finalDeltaTime を作る前の dt |

さらに編集時の水・草木にはプレビュー用更新がある。つまり「Play 停止だから全ての time が止まる」「ヒットストップだから全エフェクトも同じ割合で止まる」とは言えない。個々の時計の使い分けが、停止中の画面や手触りに現れる。

## 3. 固定更新の accumulator

`RunFixedUpdates` は経過時間を貯める accumulator を持つ。1/60 秒以上あれば一回の FixedUpdate を呼び、その分を引く。

```text
蓄積 0.010 秒 + 今回 0.020 秒 = 0.030 秒
一回 0.016667 秒進める → 約 0.013333 秒を持ち越す
```

一フレームの上限は四回。上限に達したら残りの蓄積も最大 1/60 秒へ抑える。遅いフレームで遅れを完全に取り戻そうとして更新回数がさらに増え、もっと遅くなる「追いつき処理の悪循環」を防ぐ。その代わり、全ての経過時間を必ずシミュレーションする保証は捨てている。

**ただし、固定更新の入口があることと、ゲーム全体が固定時間で動くことは別である。** [`BaseScene::FixedUpdate`](../engine/system/scene/BaseScene.cpp) は Object と Player に転送するが、[`Object3d::FixedUpdate`](../engine/graphics/3d/object/Object3d.h) の基底実装は何もしない。この調査時点の `engine` / `game` の検索では、派生側の FixedUpdate 実装は見つからない。通常の Scene Update は別途一回実行される。移動・衝突が全て固定更新へ移されている、という説明は現行コードに合わない。

将来処理を固定更新へ移す場合には、通常 Update と二重に進めないこと、入力の一回イベントを複数回消費しないこと、描画姿勢の補間をどうするかが設計上の課題になる。これは今ある機能の説明と区別した拡張時の注意点である。

## 4. 入力は「値」と「変化」を分ける

[`InputManager`](../engine/system/input/InputManager.cpp) は DirectInput、XInput、SDL の入力を扱い、現在と前回の状態を保持する。

```text
Pressed   = 現在が押下
Triggered = 現在が押下、かつ前回が非押下
Released  = 現在が非押下、かつ前回が押下
```

例えば `0,1,1,0` という四フレームなら、Pressed は `0,1,1,0`、Triggered は `0,1,0,0`、Released は `0,0,0,1`。これは入力を検出する式であり、攻撃可能か、消費するゲージがあるか、UI が入力を取るかは呼出側の判断になる。

`IsActionPressed` は KeyConfig のキー・マウス・パッドを OR する。`IsActionTriggered` と `IsActionReleased` も各デバイスのエッジを OR する。統合済みアクションの前回値と今回値から一つのエッジを作る設計ではない。

したがってキーボードを押したまま同じアクションのパッドボタンを離すと、アクションは Pressed のまま Released も true になりうる。複数デバイスを同時に使う場合や、チャージ解除の条件を読む際に重要な契約である。

## 5. スティックのデッドゾーン

スティックは手を離しても完全なゼロを返すとは限らない。小さな入力を切る範囲が dead zone である。現行の `GetLeftThumb` / `GetRightThumb` は各軸をしきい値と比較し、超えた値を 32768 で割る。円の中心からの距離で判定する radial dead zone ではない。

この方法では片方の軸だけがゼロになる領域があり、しきい値を超えた瞬間に値が跳ぶ。しきい値を引いて残りを 0〜1 に再正規化する処理とは操作感が異なる。SDL 側のスティック取得にはしきい値 3000 と Y 反転を使う経路もあるため、全入力 API が同じ補正という前提で説明しない。

`CaptureReplayState` / `ApplyReplayState` は再生用に状態を保存・適用する。現在値だけを戻し前回値を一致させなければ、押した瞬間の判定が変わる。Replay の入力記録は、単なる押下キー一覧より広い状態を扱う必要がある。

## 6. 音声の役割分担：デコードと再生

[`AudioPlayer`](../engine/system/audio/AudioPlayer.cpp) のストリーミング経路は Media Foundation の SourceReader で音をデコードし、XAudio2 の SourceVoice に再生データを渡す。SourceVoice は一つの音を再生する側、MasteringVoice は最終的な出力側である。

圧縮ファイルを読むこと、圧縮を解いて PCM データにすること、再生キューへ渡すこと、スピーカーから出ることは別の時点で起きる。`Start` を呼んだだけでファイル全体のデコードが完了しているわけではない。

## 7. リングバッファが必要な理由

`DecodeThread` はキューの空きを見て `ReadSample` し、Media Foundation のバッファをロックして取得したデータを、自分が所有する `buffers[currentBufferIndex]` へコピーする。そのアドレスを `SubmitSourceBuffer` に渡し、インデックスを剰余で次へ進める。

```text
decode → buffer[0] → 音声キュー
decode → buffer[1] → 音声キュー
...
消費された領域を次の decode に再利用
```

Media Foundation の一時データのポインタだけを渡し、すぐ Unlock / 解放すると、XAudio2 が後で読む時に有効とは限らない。コピーは再生完了までの寿命を自分側で確保するためである。リングの再利用は、キュー数の上限と FIFO の再生順を前提にしている。

キューが一杯なら condition_variable で最大 10ms 待ち、消費通知などで再確認する。音声ファイルの末尾では、ループなら先頭へ戻す。非ループなら既に投入したキューが空になるまで待つ。「デコードするデータがない」と「音が鳴り終わった」は違うためである。

## 8. 一回の再生を識別するハンドル

`PlayTransientSE` は新しい SourceVoice とデコード状態を作り、個別の PlaybackHandle を返す。同じファイルを複数回鳴らしても、再生インスタンスごとに停止・生存確認できる。

音量は 0〜1 に制限した値と SE master volume の積。pitch は 0.5〜2 に制限し `SetFrequencyRatio` に渡す。これは音程だけを保った時間伸縮とは異なり、再生レート比を変える方法である。数値が 2 なら元のサンプルを速く消費する方向になる。

`Update` は再生終了した transient を回収する。終了や停止ではデコードスレッドの終了を待ち、SourceVoice と関連リソースを破棄する。状態を先に削除すると、まだ動くスレッドが同じメモリへ触れる危険があるため、join と解放の順序が重要になる。

## 9. 問題を追う順番

停止中の演出が動く場合は、まず渡している dt の種類を確認する。入力が二回発火する場合は、現在・前回の更新時点と、同じフレームでの呼出回数を確認する。音が途切れる場合はイベント発火だけでなく、デコード、キュー残量、バッファ寿命、再生状態を分けて見る。

これらはすべて「同じ値を持つか」だけでなく「いつ更新され、いつまで有効か」が結果を決めるシステムである。
