# ノードグラフは何を編集し、どこまで実行するか

[目次](00_目次と読み方.md) / [エディター一覧](09_エディター機能一覧.md)。対象は `NodeGraphCore`、`NodeGraphTemplateRegistry`、`NodeGraphEditorWindow`、`NodeGraphExecutor`。一般的なゲームエンジンの万能ビジュアルスクリプトと同じ機能があると推測せず、現行の範囲を読む。

## 1. 四つの役割

[`Core`](../engine/utility/SystemDebug/editor/nodegraph/NodeGraphCore.cpp) は Node、Pin、Link、Property のデータと保存・検証を持つ。[`TemplateRegistry`](../engine/utility/SystemDebug/editor/nodegraph/NodeGraphTemplateRegistry.cpp) はノードの種類と標準 Pin / Property の定義。[`EditorWindow`](../engine/utility/SystemDebug/editor/nodegraph/NodeGraphEditorWindow.cpp) は描画・選択・接続操作。[`Executor`](../engine/utility/SystemDebug/editor/nodegraph/NodeGraphExecutor.cpp) は実行用の状態を持つ。

Node は処理や値の箱、Pin は接続口、Link は出力 Pin ID と入力 Pin ID の組。見えている曲線は Link の視覚表現で、線そのものにゲーム処理が埋め込まれているわけではない。ノード位置を変えてもリンク先の ID が同じなら論理的な接続は変わらない。

## 2. FlowとValueは意味が違う

Flow は「次にどの処理をするか」、Value は「どの値を渡すか」。例えば開始→待機→ログは制御の順番。数値ノード→強度入力はデータの関係。Core の `AddLink` は出力から入力か、Pin の kind と値型が互換か、入力に既存リンクがないかを確認する。

同じ入力へ複数リンクを許すと、どの値を採用するか決める追加規約が必要になる。この実装は一つの入力に一つの接続という制約を置く。接続が成立したことは、そのノードに実行処理が登録済みだという意味ではない。

## 3. 到達可能性は幅優先探索

`Validate` は Event ノードを起点に queue を使い、Flow 出力の接続先を辿る。訪問済み set へ初めて挿入できたものだけを queue に入れるため、同じノードを何度も処理しない。これは **BFS（幅優先探索）**。Value 接続を辿らないのは、値を受け取れることと実行の入口から到達できることが別だから。

`BuildExecutionPreview` も接続構造を辿って説明用の順序を作る。分岐条件の値を評価した実行結果ではない。グラフ表示に順番が出ても、ゲームをその順で実行した証拠にはならない。

## 4. 現行Executorは直列ドライラン

`Start` は指定の Event、または該当する最初の Event を選び、`BuildLinearExecutionList` で実行する Node のポインタ列を作る。各 Node の**最初の Flow 出力だけ**を追い、同じ Node の再訪は循環として拒否する。その出力に複数の Link があれば直列実行では扱えないとして失敗する。

つまり任意の分岐・繰り返しをコンパイルして実行する仮想マシンではない。見た目が複雑なグラフでも、この Executor が走らせるのは制約付きの一本の実行列。特に Value ノードはここで汎用のデータフロー評価を行うわけではなく、個々の Action Handler が必要な処理をする。

## 5. Waitはスレッドを眠らせない

`Update` は待機時間が残っていれば deltaTime を引き、残りが正ならそのフレームの実行を終える。待ち終われば while で次の Node を進め、Wait に到達したらまた戻る。ゲームループは止まらない。これは**協調的に時間を進める状態機械**であり、`sleep` でメインスレッドを停止する方式ではない。

残り0.01秒に dt=0.016秒を与えると、待機を0へ丸めて次を進める。超過0.006秒を次の Wait へ繰り越して厳密に消費する経路ではないため、細かい待機の累積ではフレーム刻みの影響がある。時間精度を評価するならこの更新規約まで見る。

## 6. Action Handlerでゲーム機能へ接続する

`RegisterActionHandler(nodeType,handler)` は文字列のノード型から関数を引く表へ登録する。ExecuteNode は種類ごとに Event、Comment、Data、Wait、Log を扱い、それ以外は登録済み handler を呼ぶ。handler が false を返すと実行を止める。`requestedWaitSeconds` が正なら演出待ちを設定する。

**未登録ノードはエラー停止ではなくスキップして進む**。ドライラン完了は全ノードのゲーム機能が実行された証明にならない。ステータス表示の「未実装ノードをスキップ」を確認し、対応する handler がどこで登録されたかまで追う必要がある。

## 7. ポインタの寿命と保存

Executor の `graph_` と `executionList_` はグラフと Node の借用参照。実行中に Node 配列の追加・削除・ロードで格納位置が変わると、保持していた Node ポインタの有効性が問題になる。開始後に元データを自由に置き換えてよい設計ではない。編集停止、再 Start、参照の再構築という境界を確認する。

Core の JSON 保存は Node / Pin / Link / Property と編集上の情報をファイルへ変換する。Executor の `waitRemaining_` や `currentIndex_` をそのまま永続化するものではない。グラフ Asset を保存しても再生途中のセーブデータにはならない。

## 8. 技術名と学べる設計

この機能で学べるのは、型付きグラフデータ、ID による参照、Registry による種類定義、BFS による到達可能性、循環検出、callback dispatch、非停止型の待機状態機械。これらが組み合わさってノード画面になる。新しい Node を追加するときは「見た目のテンプレート」「保存できる Property」「検証」「実際の handler」を一組として確認する。
